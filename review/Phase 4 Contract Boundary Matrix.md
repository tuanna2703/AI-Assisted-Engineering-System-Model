# Phase 4 — Contract Boundary Matrix

**Phase:** Phase 4  
**Revision:** 2  
**Status:** Boundary-Consistent Baseline  
**Authority:** Frozen Phase 3 AESM Operational Model, EPM, and PEM

## 1. Purpose

This matrix defines the semantic boundary between the AESM execution system and an Agent. It is a boundary specification, not yet the normative machine-readable Agent Protocol.

The matrix preserves the authority hierarchy established by the frozen Phase 3 Operational Model and the EPM/PEM distinction:

```text
EPM
  ↓ engineering meaning and validity
PEM
  ↓ execution semantics and control
AESM Operational Model
  ↓ authoritative operational representation
Agent Execution Contract
  ↓ interaction boundary
Agent
```

## 2. Foundational Boundary Rules

| Boundary | Rule |
|---|---|
| Agent / Runtime | An Agent is a Participant. It is not the Runtime. |
| Agent / EPM | An Agent does not define or redefine engineering semantics. |
| Agent / PEM | An Agent does not define or redefine execution semantics. |
| Agent / Execution Context | An Agent does not own authoritative Execution Context. |
| Agent output / authoritative state | Agent output is not authoritative merely because it was generated by an Agent. |
| Proposal / authorization | A proposal or recommendation does not constitute authorization. |
| Engineering Decision / Execution Determination | These remain distinct. |
| Engineering completion / Runtime termination | These remain distinct. |
| Observation / mutation | Observation does not itself mutate authoritative state. |

## 4. Controlled Mutation Boundary

The Agent must not silently transform its own output into authoritative state.

The general path is:

```text
Agent / Participant / Tool / Environment
                 │
                 ├── Participant Input
                 ├── Observation
                 └── Candidate Contribution
                         │
                         ▼
                Evaluation / Validation
                         │
                         ▼
              Authorized State Mutation
                         │
                         ▼
                 Execution Context
                         │
                         ▼
                  Execution Trace
```

These categories are intentionally distinct. Participant Input is not synonymous with Observation, and Candidate Contribution is not synonymous with either. The applicable recognition and mutation path depends on the type of contribution and the governing EPM/PEM semantics.

## 5. Agent Execution Boundary

An Agent may perform engineering work, but Agent execution remains within Runtime-controlled PEM execution.

```text
Agent
  ↓
requested / authorized work
  ↓
Runtime
  ↓
PEM-controlled execution
  ↓
Execution Result
  ↓
Verification / Context Update
```

The Agent does not become the Runtime by performing an execution activity. Capability to perform work does not imply authority to determine process-level execution outcomes.

## 6. Authority Preservation

The Agent may contribute to execution but may not:

- redefine EPM semantics;
- redefine PEM semantics;
- silently mutate authoritative Execution Context;
- convert its own output directly into authoritative engineering state;
- declare an Engineering Decision authoritative merely because it generated it;
- independently establish an Execution Determination where PEM authority is required;
- bypass Decision Gates;
- fabricate participant approval;
- erase historical state;
- silently alter the Engineering Objective;
- conceal material uncertainty to preserve forward progress.

## 7. Boundary Review Result

Revision 2 incorporates the two corrections identified by the Phase 4 boundary consistency review:

1. Agent execution is explicitly Runtime-mediated and PEM-controlled.
2. Participant Input, Observation, and Candidate Contribution remain distinct categories in the controlled-mutation path.

No change to the frozen Phase 3 semantic baseline is required.

## 8. Promotion Criterion

This matrix may serve as the direct basis for the normative Agent Execution Contract once Revision 2 verification confirms consistency with the frozen Phase 3 Operational Model, EPM, and PEM.

The matrix itself does not define transport, serialization, API, tool-call, or implementation-specific protocol details. Those belong to the subsequent protocol specification.
